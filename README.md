# 物聯網 Final Project Proposal

- 主題：個人化天氣主播
- 痛點：不同人對空氣品質、溫濕度的耐受度不一樣，且行前上完查詢不同的氣象資料太花時間
- 解法：整合天氣資料與使用者習慣，打造客製化天氣預報網站
- 功能：抓取天氣資料、空氣品質，使用者行前詢問時可以提供帶傘、擦防曬、戴口罩……的建議

## 一、摘要

氣象預報與空氣品質監測資料為民眾規劃日常活動的重要參考依據，然而，政府開放資料平台主要著重於環境數據的查詢與呈現，使用者仍需自行整合不同來源的環境資訊，並依據活動情境與個人需求進行判斷。此外，現有天氣資訊服務多以通用性預報為主，對於個人偏好、活動情境與環境風險因素的整合仍有改善空間，因而難以直接提供符合個別需求的行前建議。

既有研究已探討大型語言模型於天氣資訊對話式查詢、空氣品質資料解讀及個人化推薦等領域的應用，但在本研究回顧的文獻中，尚未充分驗證同時整合多源環境資料、個人偏好與日常行動建議，並兼顧資料品質及判斷依據可追溯性的系統。此外，氣象預報具有不確定性，若系統未適當揭露資料限制或過度簡化預報資訊，可能增加使用者誤解或過度信任建議的風險。因此，如何將官方環境資料轉換為符合個人需求、具情境相關性且可追溯的行動建議，為本研究欲解決的核心問題。

本研究提出一套「個人化天氣助理」（Personalized Weather Assistant）AI Agent 系統，旨在整合氣象與空氣品質資料，針對使用者規劃的多站行程，提供符合地點、時段、活動情境及個人偏好的行前建議。

系統採用混合式架構，整合中央氣象署天氣預報資料與環境部空氣品質監測及預報資料。首先，將使用者輸入的行程標準化為地點、時間區間、活動型態與戶外暴露程度，並針對各行程段進行資料時空對齊與品質檢查。接著，由結合領域知識的規則決策引擎，依據降雨、紫外線、空氣品質及冷熱舒適等環境條件與使用者偏好產生結構化建議；大型語言模型（Large Language Model, LLM）則負責使用者需求解析、建議內容解釋與後續問答，並依據既有決策結果提供自然語言說明，以避免生成內容偏離原始判斷。此外，系統納入個人偏好管理與行後回饋機制，支援使用者確認後的偏好調整，並保留建議依據與資料限制，以利後續追溯與驗證。

本研究預計比較「僅呈現官方環境數據」、「固定規則結合文字模板」及「整合規則引擎、個人偏好與 LLM」三種方法，並設計多站跨鄉鎮行程、高降雨機率、高紫外線指數、相同 AQI 但主要污染物不同，以及資料缺漏、過期或超出空氣品質預報範圍等測試情境。評估指標涵蓋建議可重現性、重要提醒遺漏率、資料限制揭露率、使用者對建議符合程度與實用性之評分、建議可理解性，以及 API 請求成功率與系統回應時間。預期本研究所提出之系統能降低使用者跨平台查詢與自行整合環境資訊的負擔，並提升行前建議之個人相關性、可理解性、實用性及可追溯性。

**關鍵字：** AI Agent、個人化推薦、氣象資訊整合、空氣品質、領域知識、大型語言模型

## 二、緒論

## 2.1 研究背景與動機

隨著氣象資訊與環境監測技術的發展，使用者能夠透過網路取得天氣預報、降雨機率及空氣品質等資訊，作為日常活動安排的參考。例如，出門前確認降雨機率可以協助使用者決定是否攜帶雨具，而空氣品質指標（Air Quality Index, AQI）則能提供環境空氣污染程度的參考。以臺灣為例，中央氣象署提供氣象開放資料，環境部亦提供空氣品質指標及污染物監測資料，顯示整合多種環境資訊具有實際的資料來源與技術基礎。

然而，取得環境資訊並不代表使用者能立即做出符合自身需求的決策。不同使用者對溫度、濕度及空氣品質的主觀感受與關注程度可能有所差異。例如，容易感到悶熱的使用者可能特別關注高溫與濕度，重視防曬的使用者可能優先確認紫外線指數，而容易過敏的使用者則可能更在意 AQI 的變化。因此，除了提供客觀的環境數據之外，如何依據個人偏好將資訊轉換成具體、易理解且可執行的行前建議，是值得探討的問題。

## 2.2 問題定義與既有方法的限制

目前，使用者可以透過天氣預報服務及空氣品質監測平台查詢相關資訊。然而，當使用者需要同時考量降雨、溫度、濕度、紫外線及空氣品質時，可能需要切換不同的資訊來源(如下表)，再自行判斷是否應攜帶雨傘、做好防曬或準備口罩。這種由使用者自行整合資訊並做出決策的方式，可能增加行前查詢的操作負擔。

| 降雨      | 每日雨量 - 交通部中央氣象署   |
| --------- | ----------------------------- |
| 溫度/天氣 | 首頁-交通部中央氣象署         |
| 紫外線    | 紫外線觀測 - 交通部中央氣象署 |
| 空氣品質  | 首頁 - 空氣品質監測網         |

此外，一般化的天氣資訊主要呈現特定地區與時間的環境狀況，未必能直接回應每位使用者的個人偏好。例如，在相同的氣溫下，不同使用者對炎熱或寒冷的感受可能不同；即使面對相同的空氣品質資訊，不同使用者對相關資訊的關注程度也可能有所差異。因此，若系統僅提供環境數據，而未進一步考量使用者的個人需求，其資訊仍可能需要使用者自行解讀與轉換。

基於上述問題，本專題將探討如何整合天氣與空氣品質資料，並結合使用者設定的個人偏好，降低行前資訊查詢與判斷的負擔。

## 2.3 研究方法與創新之處

本專題旨在開發一套「個人化天氣助理」（Personalized Weather Assistant）網站，整合氣象與空氣品質資料，並依據使用者的個人偏好提供客製化的行前建議。

在系統設計上，首先取得指定地區與時間的天氣及空氣品質資訊，再結合使用者設定的偏好，例如對高溫、低溫、濕度及空氣品質的關注程度。接著，系統依據環境數據與預先定義的判斷規則，產生相應的行動建議，例如依降雨預報提醒使用者攜帶雨具、依紫外線資訊提醒使用者做好防曬，以及依空氣品質狀況提供適當的防護提醒。

本專題的主要特色，在於將傳統以環境資訊呈現為主的天氣查詢方式，延伸為結合個人偏好與行動建議的資訊服務。系統並非改變或重新預測客觀天氣，而是針對相同的環境條件，依據不同使用者的需求提供不同的資訊呈現與建議，以提升資訊的個人相關性與實用性。

## 2.4 預期貢獻

本專題預期具有以下貢獻：

1. **環境資料整合：** 整合天氣預報與空氣品質資料，建立統一的資訊呈現介面，減少使用者切換不同資訊來源的需求。
2. **個人化偏好設定：** 設計使用者偏好設定機制，讓系統能依據使用者對溫度、濕度及空氣品質等面向的關注程度，調整建議內容。
3. **行前建議產生機制：** 建立結合環境條件與個人偏好的判斷規則，將原始環境數據轉換為具體的出門準備建議。
4. **系統實作與使用者評估：** 完成個人化天氣助理網站，並透過功能測試及使用者回饋，評估系統的資訊整合效果、建議合理性與操作便利性。

綜合而言，本專題希望透過環境資料整合與個人化推薦機制，讓使用者不僅能知道外在環境的狀況，也能更有效率地判斷自己出門前應做哪些準備，進而提升天氣資訊在日常生活中的實用價值。

## 三、相關研究

## 3.1 AI 技術面

**(1) LLM Agent 應用於天氣資訊解讀**

在天氣資訊的對話式應用方面，Weathernews 於 2025 年 1 月推出生成式 AI 功能「Weather Agent」，讓使用者以對話方式查詢天氣資訊 [1]。這個案例展示了以自然語言呈現天氣資訊的應用方式；不過，就本專題回顧的研究與產品資料而言，尚未看到依個人健康狀況或環境耐受度調整日常行動建議的完整評估。

**(2) LLM 應用於空氣品質與健康建議**

Pan 與 Nipu [2] 以 Model Context Protocol（MCP）連接 LLM 與即時空氣品質監測資料，讓使用者透過對話查詢監測資訊。6 位專家以五點量表評估 15 則系統回答，事實正確性平均為 4.78 分；然而，研究也指出評分者一致性偏低，且評估規模有限，因此這項分數應解讀為小規模專家評分結果，而非模型的整體正確率。另一項研究以 2025 年洛杉磯野火期間的空氣品質為案例，採用 Instructor–Worker 多代理人架構，並以 Google Air Quality API 提供的健康建議作為參考文本，使用 BERTScore 評估生成建議的語意相似度 [3]。這些研究呈現了 LLM 結合工具呼叫與即時環境資料的應用方式；其中 [3] 的健康建議依族群分類（如健康成人與肺部疾病患者），兩項研究均未依個別使用者的耐受度建立模型。

**(3) 個人化 LLM 與記憶模組**

2025 年的 LLM 推薦代理人綜述將相關架構整理為 Profile、Memory、Planning 與 Action 等組件 [4]。Memory-Assisted LLM 推薦系統則依據當前查詢，從使用者歷史紀錄中選取相關資料作為記憶，而非將全部紀錄輸入模型；研究以電影與書籍評分預測任務評估此方法 [5]。本專題的「使用者耐受度檔案」參考其選擇性檢索概念，在產生建議時擷取與當前天氣及健康情境相關的個人紀錄。

**(4) LLM 在氣象影響理解上的研究限制**

WXImpactBench [6] 建立劇烈天氣社會影響的評測基準，並指出此領域的 LLM 能力仍需進一步研究；研究也提到高品質語料蒐集與評測基準建立上的挑戰。該研究聚焦於劇烈天氣及其社會影響，並未直接評估日常天氣決策。因此，本專題將由規則模組處理指標計算與門檻判斷，再由 LLM 負責解釋結果及回應對話。這是本專題的系統設計選擇，其可靠性仍須透過後續測試驗證。

## 3.2 領域知識面

**(1) 熱舒適的個體差異**

Abdulraheem、Lee 與 Jung [7] 提出結合長短期記憶網路（LSTM）與強化學習的個人化熱舒適模型 PCM-RL。研究顯示，此模型能處理室內環境下熱感覺、舒適度與偏好的時間變化及個體差異。由於該研究聚焦室內環境，其結果不能直接代表戶外情境；本專題將參考其個人差異建模概念，並依戶外氣象資料設計建議方式。

**(2) 台灣戶外熱環境**

Shih、Huang 與 Hwang [8] 使用 1990 至 2023 年台北與台中的逐時氣象資料計算通用熱氣候指數（UTCI），並比較都市中心與郊區的戶外熱舒適變化。研究指出，在其分析的地點與期間內，都市熱島效應對戶外熱舒適的影響大於氣候變遷；台北與台中的變化幅度亦有所不同。這項研究顯示，評估戶外熱環境時需要考量城市與區域差異，但並未直接分析個人耐熱程度。

**(3) 空氣品質（PM2.5）與健康**

Sun 等人 [9] 使用美國成人健康保險資料進行病例時間序列研究，發現短期暴露於低於 2021 年 WHO 空氣品質指引值的 PM2.5，仍與部分住院及呼吸道急診就醫結果相關。此研究支持低濃度 PM2.5 仍可能伴隨健康風險，但其研究對象與情境為美國人口及 PM2.5 暴露，不能直接用來訂定台灣 AQI 分級或個人化口罩建議門檻。本專題將依適用的官方健康指引制定防護建議。

**(4) 紫外線指數：從資訊呈現到行動提示**

Kaiser 等人 [10] 的系統性回顧與統合分析指出，民眾對全球太陽紫外線指數（UVI）的認知程度會因地區而異，而納入研究所涵蓋地區的 UVI 使用程度普遍偏低。這顯示呈現指數與協助使用者理解、採取防護行動之間仍有落差。本專題因此將 UVI 資訊轉換為具體的防曬提示；此設計的實用性仍須透過後續評估確認。

**(5) 降雨機率的理解**

Joslyn、Nadav-Greenberg 與 Nichols [11] 透過三項心理學實驗探討民眾對降雨機率的理解，發現部分受試者會將降雨機率誤解為降雨時間或降雨面積的比例；答錯的受試者也較傾向表示會穿外套或帶傘，顯示他們可能把降雨機率當成確定會下雨。研究對象主要是美國太平洋西北地區的大學生，因此結果不宜直接推論為所有民眾的理解程度。本專題將以文字解釋降雨機率，並提供個人化帶傘建議，作為降低資訊理解負擔的設計方向。

**(6) 影響導向預報**

世界氣象組織（WMO）於 2015 年發布影響導向預報與警報服務指引 [12]。該指引強調預報與警報服務應考量危害可能造成的影響，並協助相關單位及民眾採取行動，其主要面向多重危害與警報服務。本專題借鏡其將預報資訊連結至影響與行動的理念，將天氣與空氣品質資訊轉換為日常出門前可參考的建議。

## 3.4 Existing Research → Limitations → Research Gap → Our Project

**Existing Research：** AI 應用方面，已有商業天氣對話功能 [1]，也有結合 MCP 或多代理人架構處理空氣品質資料、產生健康建議的研究 [2][3]。個人化推薦研究則提出使用者 Profile 與記憶檢索等設計 [4][5]。領域研究指出室內熱舒適具有個體與時間差異 [7]，台灣戶外熱舒適會因城市及都市化情形而異 [8]；低濃度 PM2.5 暴露與健康結果的關聯亦受到研究 [9]。此外，既有研究指出 UVI 使用程度偏低 [10]，部分民眾會誤解降雨機率 [11]；WMO 指引則提供將預報資訊連結到影響與行動的理念 [12]。

**Limitations：**

1. 本節回顧的天氣與空品系統，主要展示資訊解讀或依族群分類產生建議；相關文獻尚未呈現依個人耐受度檔案調整建議的完整驗證。
2. 熱舒適個人化研究 [7] 聚焦室內環境，其結果不能直接代表戶外熱環境。
3. 天氣、空氣品質與紫外線等資訊來自不同資料來源；如何整合並轉換為一致的日常行動建議，仍是本專題要處理的系統設計問題。
4. LLM 在劇烈天氣影響理解方面已有專門評測基準 [6]，但該研究未涵蓋本專題關注的日常出門情境；生成建議的可靠性仍需依實際任務測試。

**Research Gap：** 在本節回顧的文獻中，尚未看到一套經完整驗證的系統，同時整合多源天氣與空氣品質資料、依據使用者紀錄建立耐受度檔案，並將資訊轉換為日常行前行動建議。因此，本專題聚焦於這些功能的整合與評估。此研究缺口是根據本節回顧範圍所作的歸納。

**Our Project：** 本專題提出「個人化天氣主播 Agent」，以中央氣象署與環境部開放資料為資料來源，結合 UTCI 或體感溫度、AQI、UVI 與降雨機率等資訊。系統由規則模組負責指標計算與門檻判斷，再依使用者耐受度檔案調整建議，最後由 LLM 以自然語言說明建議內容及依據。系統建議的可靠性與實用性將透過後續測試評估。

## 四、三大核心問題

### Q1. 五個核心思維模式

#### 1. 以使用者的行動與影響為中心

#### 意義

使用者查詢天氣，通常是為了決定如何穿著、是否攜帶雨具，以及是否調整戶外活動。因此，系統應從使用者需要做出的決定出發，選擇並解釋相關資訊。

除了呈現環境數值，也應說明這些條件可能帶來什麼影響，以及使用者可以採取哪些行動。

#### 證據

WMO 的影響導向預報將氣象危害與暴露、脆弱度結合，目的在於支援決策，促成適當行動。

這提供本專題從數據呈現走向行動建議的理論基礎，但不能直接證明日常個人化天氣助理一定有效，仍須透過使用者評估驗證。

來源：WMO：Communicating for Life-saving Action

#### 如何影響系統設計

- 輸出同時包含環境條件、可能影響與建議行動。
- 納入出門時間、目的地與戶外活動時間，提高建議的情境相關性。
- 評估使用者是否更快完成準備，而不只評估介面美觀或文字流暢度。

#### 本專題範例

將「午後降雨機率偏高」轉換成：

> 你預計下午步行外出，建議攜帶雨具，並在出發前再次確認最新預報。

### 2. 相同環境條件，不代表相同的個人感受與需求

#### 意義

氣溫與濕度是環境資訊，舒適程度則與個人偏好及活動情境有關。

因此，個人化應調整資訊的重要性與建議內容，而不是改寫客觀天氣。

#### 證據

PCM-RL 研究結合 LSTM 與強化學習，處理熱感覺、舒適及偏好的時間變化與個體差異。

不過，該研究聚焦室內環境，不能直接將其效果外推到戶外行前建議。

來源：Dynamic personalized thermal comfort model

#### 如何影響系統設計

- 分開保存環境資料、使用者偏好與活動情境。
- 初期由使用者明確設定怕熱、怕冷等偏好。
- 若後續加入回饋學習，應記錄當時的活動、時間與環境，避免把情境差異誤認為個人特性。
- 將使用者自述偏好與系統推估結果分開標示。

#### 本專題範例

同樣的氣溫下，怕冷者可能收到攜帶薄外套的提醒，其他使用者則不一定需要。

### 3. 預報具有不確定性，建議應考慮判斷錯誤的代價

#### 意義

降雨機率不能直接轉換成「一定會下雨」或「一定不會下雨」。

是否攜帶雨具，除了降雨機率，也取決於攜帶負擔、淋雨後果與替代方案。

#### 證據

中央氣象署說明，降雨機率是特定地區、預報時段內發生降雨的機率，與降雨強度及累積雨量沒有直接對應關係，應結合風險觀念使用。

來源：中央氣象署：氣象常識問答集

#### 如何影響系統設計

- 保留原始機率與預報時段，避免使用過度確定的表述。
- 讓使用者表達不想帶傘、非常不希望淋雨等偏好。
- 區分短暫外出與長時間戶外活動等不同情境。
- 當資料不足或預報更新時，允許系統保留判斷或修正建議。

#### 本專題範例

以簡化的決策模型為例：

- $p$：與決策情境相符的遇雨機率。
- $C$：攜帶雨具的成本。
- $L$：未攜帶雨具而遇雨的損失。
- $r$：攜帶雨具可以避免的損失比例。

當下式成立時，攜帶雨具具有較低的預期成本：

$$
p \times rL > C
$$

這個模型用來說明個人化門檻的概念。實作時，仍須確認預報機率與使用者的活動地點、時段及暴露情境是否相符，不能直接將區域降雨機率視為個人遇雨機率。

### 4. 個人舒適偏好與健康防護應分開處理

#### 意義

「我覺得不熱」與「沒有熱傷害風險」不同；「我不在意空氣品質」也不能證明暴露沒有風險。

因此，個人化不能只依滿意度或主觀感受決定健康相關提醒。

#### 證據

BMJ 的美國保險人口研究發現，低於 WHO 日均 PM2.5 指引值的暴露，仍與部分住院及急診結果有統計關聯。

這支持低濃度不等於零風險，但無法直接推導特定使用者的口罩提醒門檻。

WHO 另建議，UV 指數達到 3 以上時，應採取防曬措施。

來源：

- BMJ：低濃度 PM2.5 短期暴露研究
- WHO：Ultraviolet radiation

#### 如何影響系統設計

- 舒適偏好可以調整提醒門檻與呈現優先順序。
- 健康防護依官方指引與適用族群處理。
- 不以使用者沒有不舒服，作為降低防護建議的唯一依據。
- 空品建議須考慮主要污染物，避免只根據 AQI 數字產生相同提醒。

#### 本專題範例

環境部的 AQI 由各污染物副指標的最大值決定。因此，相同 AQI 可能由不同污染物主導，系統應保留主要污染物資訊，再依對應指引產生建議。

來源：環境部：空氣品質指標

### 5. 建議必須可追溯，資料品質與生成文字需要分層驗證

#### 意義

建議是否可信，取決於資料來源、適用時間與地點、判斷規則，以及最後文字是否忠實呈現結果。

語句流暢只是品質的一部分，不能代替正確性驗證。

#### 證據

LLM 空品介面研究透過 MCP 將回答連接至即時資料，專家評估的事實正確性為 4.78／5，顯示資料接地具有潛力，但不能解讀成所有情境都不會出錯。

WXImpactBench 則提供天氣影響理解的專門評測，反映這類能力需要獨立驗證。

來源：

- LLM-enhanced Air Quality Monitoring Interface via Model Context Protocol
- WXImpactBench

#### 如何影響系統設計

- 保存資料來源、測站或地區、發布時間及有效時段。
- 區分觀測值與預報值，不能將現在的 AQI 當成明天的 AQI。
- 先以程式產生結構化判斷，再由 LLM 解釋。
- 檢查生成文字是否改動數字、遺漏重要提醒或加入無依據內容。
- 資料缺失時顯示限制，不能讓 LLM 自行補值。

#### 本專題範例

建議內容可以附上：

> 判斷依據：指定時段的降雨預報與使用者步行情境。資料更新時間及來源可展開查看。

### Q2. 三個重要專業爭論

### 爭論一：固定規則判斷 ↔ LLM 自主產生建議

#### 觀點 A：以領域規則為核心

規則能明確處理門檻、優先順序與例外，容易測試與追溯。

對數值比較及官方防護指引而言，結果較容易保持一致。

#### 觀點 B：由 LLM 綜合情境判斷

LLM 能理解自然語言需求，處理「下午走路去上課、晚上騎車回家」等複合情境，並產生容易理解的說明。

#### Evidence：雙方證據與限制

AI-Meteorologist 展示將數值預報轉換成敘事報告的能力；Instructor-Worker 系統則探索從空品資料產生健康相關建議。

這些研究支持 LLM 的整合與表達潛力，但沒有直接證明其適合取代本專題所有門檻判斷。

規則方法的可重現性來自明確的程式邏輯，但規則本身是否合理，仍取決於來源、適用條件與驗證結果。

來源：

- AI-Meteorologist
- Instructor-Worker LLM System

#### Consensus：目前可確立的共同要求

建議需有可靠資料依據，並接受任務評估。

至於規則與 LLM 的最佳分工，現有證據不足以宣稱已有單一共識。

#### Unresolved Problems：尚未解決的問題

- 哪些情境可以交由 LLM 判斷，哪些需要明確規則？
- 規則互相衝突時，如何決定建議優先順序？
- 如何證明自然語言解釋帶來的效益，足以抵銷成本、延遲及錯誤風險？
- 如何避免 LLM 在解釋時擅自改變判斷結果？

#### 對本專題的設計決策

採用混合架構：

- 規則處理數值判斷與防護條件。
- LLM 處理需求解析及結果解釋。
- 以固定文字模板作為比較基準，驗證加入 LLM 的實際效益。

### 爭論二：統一標準 ↔ 學習個人耐受度

#### 觀點 A：使用一致的標準與建議

統一標準容易理解、維護與比較，對沒有歷史資料的新使用者，也能立即提供服務。

#### 觀點 B：依個人資料持續調整

不同人的舒適感與行動成本不同，固定門檻可能造成過度提醒或提醒不足。

使用者回饋與記憶有機會提升建議的個人相關性。

#### Evidence：雙方證據與限制

PCM-RL 支持熱舒適建模需要考慮個體及時間差異。

Memory-Assisted LLM 在推薦任務中，展示選擇性擷取相關記憶的效益。

不過，兩者並未直接驗證戶外天氣健康建議中的個人耐受度學習，因此不能直接宣稱相同效果會出現在本專題。

來源：

- Dynamic personalized thermal comfort model
- Memory Assisted LLM for Personalized Recommendation System

#### Consensus：目前可確立的共同要求

個人差異值得納入，但偏好資料不等同於健康風險證據。

個人化可以調整哪些內容、需要多少資料，仍須依任務驗證。

#### Unresolved Problems：尚未解決的問題

- 新使用者沒有紀錄時，如何處理冷啟動？
- 一次「覺得太熱」的回饋，反映的是體質、衣著還是活動量？
- 偏好隨季節改變時，舊記憶應保留多久？
- 如何用最少的個人資料達成有效個人化？
- 如何避免系統將偶發回饋學成長期偏好？

#### 對本專題的設計決策

先完成手動偏好設定。

若後續加入學習，先調整舒適提醒及資訊排序；健康防護另依官方指引處理。

在尚未建立並評估更新機制前，使用「依個人偏好提供建議」，而非「自動學習個人耐受度」描述系統功能。

### 爭論三：簡單明確的行動建議 ↔ 保留機率、條件與不確定性

#### 觀點 A：提供直接、容易採取的建議

「建議帶傘」比一組氣象數字更容易使用，符合降低行前判斷負擔的目標。

#### 觀點 B：保留原始資訊與限制

過度簡化可能把機率變成保證，也可能掩蓋測站距離、資料時間與個人活動差異，造成錯誤信任。

#### Evidence：雙方證據與限制

WMO 強調能促成行動的風險溝通；中央氣象署則明確區分降雨機率與雨量、強度。

兩者共同指出，資訊需要能支援行動，也必須維持正確意義。

但這些原則尚不能決定本專題最適合的介面資訊量，仍需實際測試。

來源：

- WMO：Communicating for Life-saving Action
- 中央氣象署：氣象常識問答集

#### Consensus：目前可確立的共同要求

行動建議與透明資訊可以並存，但目前資料不足以確定最適合本專題的呈現密度。

#### Unresolved Problems：尚未解決的問題

- 顯示多少資訊，才不會增加操作負擔？
- 使用者是否會將建議誤認成保證？
- 頻繁提醒是否會造成忽略通知？
- 如何區分必要提醒與低優先度資訊？
- 如何讓使用者理解資料缺失與預報更新？

#### 對本專題的設計決策

採分層呈現：

1. 第一層顯示主要行動建議。
2. 第二層提供簡短原因。
3. 展開後可查看原始數值、來源、有效時段與限制。

透過使用者測試，檢查理解程度、決策時間，以及是否產生錯誤信任。

### Q3. 十個深度理解問題

### 1. Why：為什麼相同環境數據，可以產生不同的行前建議？

#### 問題

兩位使用者位於相同地點、面對相同天氣，為什麼系統仍可能提供不同建議？個人化應改變什麼？

#### 回答應掌握的重點

- 客觀環境數據應保持一致。
- 建議可隨偏好、活動、暴露時間及行動成本調整。
- 個人化不能任意改寫預報或官方風險資訊。
- 應能解釋建議差異來自哪一項使用者條件。

### 2. What-if：沒有不舒服，是否代表不需要防護提醒？

#### 問題

若使用者反覆回報「空氣不好時也沒有不舒服」，系統是否應逐步停止防護提醒？

#### 回答應掌握的重點

- 沒有主觀症狀不能證明沒有健康風險。
- 舒適偏好與健康防護需要分開處理。
- 回饋可以調整資訊呈現，但不能單獨推翻防護依據。
- 應依官方指引、適用族群及暴露情境判斷。

### 3. Trade-off：相同降雨機率，是否應有相同帶傘門檻？

#### 問題

兩人面對相同降雨機率，一人只步行五分鐘，另一人需要戶外工作兩小時，是否應有相同帶傘門檻？

#### 回答應掌握的重點

- 降雨機率不是唯一的決策因素。
- 需要考慮暴露情境、淋雨代價、攜帶負擔與替代方案。
- 區域時段降雨機率不一定等於個人活動期間的遇雨機率。
- 個人化門檻需要清楚的假設與驗證。

### 4. Failure Case：多源資料更新時間不一致會造成什麼問題？

#### 問題

天氣預報已更新，但空品資料停留在六小時前，系統仍生成完整的行前建議，可能出現什麼問題？

#### 回答應掌握的重點

- 不同時間的資料可能被錯誤組合成同一時刻的環境狀況。
- 應檢查資料新鮮度與有效時段。
- 過期資料應標示，必要時限制相關結論。
- LLM 不應自行補出缺失或過期的環境數值。

### 5. Evidence：文字比較親切，是否代表系統更有效？

#### 問題

若使用者覺得 AI 文字比較親切，是否足以證明個人化助理比一般天氣網站更有效？

#### 回答應掌握的重點

- 親切度不等於正確性或決策效益。
- 還需評估理解程度、準備時間與建議合理性。
- 必須檢查錯誤率及重要提醒遺漏率。
- 應設置適當的比較組，避免只依主觀喜好下結論。

### 6. Comparison：如何公平比較規則、模板與 LLM？

#### 問題

如何公平比較「固定規則＋模板」「固定規則＋LLM」與「LLM 自主建議」三種方法？

#### 回答應掌握的重點

- 使用相同的資料、使用者條件與測試情境。
- 採用一致的評分規準。
- 比較正確性、遺漏、可理解性、延遲及成本。
- 對生成式方法進行多次測試，觀察結果變異。
- 避免只比較文筆，或讓不同方法取得不同資訊。

### 7. Design Decision：新使用者沒有歷史紀錄時，如何個人化？

#### 問題

新使用者完全沒有歷史紀錄時，系統應直接推估其耐受度，還是先詢問偏好？

#### 回答應掌握的重點

- 需要權衡冷啟動、填寫負擔與推估可靠度。
- 可先採少量明確設定及可修改的預設值。
- 不應將未經確認的推估當成確定事實。
- 後續回饋應有足夠情境資訊，才能合理更新偏好。

### 8. Real-world Scenario：跨地區行程應如何產生建議？

#### 問題

使用者早上在甲地、下午到乙地，晚上才回家，只使用目前所在地資料會漏掉什麼？

#### 回答應掌握的重點

- 建議應對應目的地與活動時段。
- 移動過程中的暴露情境也可能重要。
- 現在觀測不能直接代表未來環境。
- 多地點建議應整合優先順序，避免產生大量重複提醒。

### 9. Failure Case／Comparison：相同 AQI 是否代表相同防護方式？

#### 問題

兩個地區的 AQI 相同，一地由 PM2.5 主導，另一地由臭氧主導，系統能否直接產生完全相同的防護文字？

#### 回答應掌握的重點

- AQI 是由污染物副指標形成的摘要指標。
- 相同 AQI 不代表污染物組成相同。
- 應檢查主要污染物與對應防護指引。
- 不能由單一數字推定所有防護方式。

### 10. Design Decision／Evidence：滿意度與重要提醒衝突時，如何決定？

#### 問題

若個人化版本的滿意度較高，卻更常遺漏重要提醒，是否應採用？應如何改善？

#### 回答應掌握的重點

- 滿意度與可靠性須分開評估。
- 先訂定重要提醒必須符合的通過條件，再優化個人化。
- 檢查遺漏集中在哪些族群與情境。
- 分析問題來自資料、規則、個人化機制或文字生成。
- 修改後需重新檢查相關失敗案例。

## 五、proposed scheme

## 1. 設計目標

本系統協助使用者針對臺灣境內的多站行程，理解每個停留站在指定時段的天氣與空氣品質情況，並依活動與個人偏好產生可採取的建議。系統的核心價值不是顯示更多數字，而是把官方資料轉為「此站、此時段、此使用者應採取什麼準備」的可追溯結論。

### 1.1 設計原則

1. **資料優先**：建議必須由官方資料與明確規則產生，LLM 不得補造資料或改寫判定結果
2. **行程分段**：每一個停留站獨立取數與判斷，最後再彙整全行程
3. **健康與舒適分離**：空品與防護提醒使用官方資料及規則；冷熱偏好只調整舒適提醒與呈現優先級
4. **不確定性可見**：資料過期、缺漏、空間解析度不足或尚無預報時，系統必須說明限制
5. **個人化須可控制**：長期偏好只能由使用者設定或確認後更新

## 2. 系統範圍與使用情境

使用者建立一份行程，其中每站包含地點、停留時間、活動型態與戶外暴露程度。例如：

```
2026-10-21
09:00-12:00  臺中市南區  步行上課       一般戶外暴露
14:00-17:00  彰化市      戶外活動       長時間戶外暴露
19:00-21:00  臺中市南區  騎車返家       一般戶外暴露
```

系統不分析臺中至彰化的移動路線，只針對三個使用者指定的停留站提出建議。

### 4.1 官方資料來源

```

若行程段超出官方空品預報範圍：仍提供天氣建議；空品顯示「尚無官方預報」，不產生空品風險判定
```

## 6. 領域規則與 LLM 責任邊界

### 6.1 規則引擎

規則引擎必須版本化，並對每個建議輸出 `ruleId` 與輸入證據。第一版規則只涵蓋：

1. **降雨準備**：降雨預報、戶外暴露時段與雨天接受度
2. **紫外線防護**：UV 資訊、戶外暴露程度與防曬重視度
3. **空品防護**：AQI、主要污染物、資料類型與空品提醒敏感度
4. **冷熱舒適**：溫濕度、活動與偏冷／偏熱傾向
5. **資料品質**：資料不可用、過期、空間粒度不足或時段不符時，降低或停止相應判定

健康防護與主觀舒適不可混用。使用者偏好可以降低提醒的呈現優先級，但不能刪除由官方資料觸發的重要防護提醒。

### 6.2 LLM

LLM 只能執行下列工作：

- 將使用者的自然語言補充轉成結構化欄位，並要求使用者確認不確定欄位
- 依 `TripRecommendation` 改寫為容易理解的行程摘要
- 回答「為什麼這樣建議？」；答案只能引用既有 `SegmentDecision.evidence` 與 `limitations`

LLM 不得自行取得未記錄的數值、修改優先級、把即時資料寫成預報，或對資料不足的時段編造結論。

## 8. Pseudocode

```
Algorithm 1: Personalized Weather Anchor Agent
Input : User U, Itinerary I, Explicit Preferences P
Output: Trip Recommendation TR

01: Validate user account U and retrieve profile P
02: Validate every itinerary segment in I
03: if a segment has no valid Taiwan location, time, or activity then
04:     return request for missing or invalid fields
05: end if
06: Normalize each segment into location, township, air-quality area, and time window
07: Initialize an empty list Decisions
08: for each normalized segment S in I do
09:     WeatherData <- retrieveCWAForecast(S.township, S.timeWindow)
10:     AirData <- selectAirQualityData(S.timeWindow)
11:     if S is current or in progress then
12:         AirData <- retrieveNearestMoENVStation(S.latitude, S.longitude)
13:     else if S matches an official next-day forecast then
14:         AirData <- retrieveMoENVForecast(S.airQualityArea, S.date)
15:     else
16:         AirData <- unavailable("No official air-quality forecast")
17:     end if
18:     Snapshot <- alignAndValidate(WeatherData, AirData, S)
19:     if Snapshot has missing, stale, or spatially unsuitable critical data then
20:         Decision <- createLimitedDecision(S, Snapshot.qualityFlags)
21:     else
22:         RainAlerts <- evaluateRainRules(Snapshot, S, P.rainTolerance)
23:         UVAlerts <- evaluateUVRules(Snapshot, S, P.sunProtectionPriority)
24:         AirAlerts <- evaluateAirQualityRules(Snapshot, S, P.airQualityAlertSensitivity)
25:         ThermalAlerts <- evaluateThermalComfortRules(Snapshot, S, P.thermalPreference)
26:         Decision <- combineAlerts(RainAlerts, UVAlerts, AirAlerts, ThermalAlerts)
27:         Decision <- attachEvidenceAndRuleIds(Decision, Snapshot, P)
28:     end if
29:     append Decision to Decisions
30: end for
31: TR <- aggregateItineraryDecisions(Decisions)
32: TR <- prioritizeCriticalProtectionBeforeComfort(TR)
33: persistDecisionRecord(U, I, TR)
34: TR.explanation <- generateExplanationFromStructuredRecord(TR)
35: return TR
```

## 9. 帳號、記憶與回饋

系統保存三種彼此分離的資料：

1. **明確偏好**：由使用者設定，隨時可檢視、修改與刪除
2. **行程紀錄**：保存使用者輸入、當時使用的資料快照與系統建議，供追溯與評估
3. **行後回饋**：使用者對實際遭遇天氣／空品與建議符合度的問卷結果

系統可根據多筆回饋建立 `PreferenceUpdateCandidate`，但不得直接覆寫 `UserProfile`。使用者接受候選調整後才建立新的偏好版本。

## 10. 評估設計

### 10.1 比較組

- Baseline A：僅顯示官方天氣與 AQI 原始數值
- Baseline B：固定規則與固定文字模板
- Proposed：規則引擎 + 個人偏好 + LLM 說明

### 10.2 測試情境

- 多站、跨鄉鎮、不同停留時段
- 有降雨機率且使用者不願攜帶雨具
- 高 UV 且長時間戶外活動
- 相同 AQI、不同主要污染物
- 當前測站資料與隔日空品預報的切換
- 資料過期、缺漏或超出空品預報範圍

### 10.3 指標

| 類型     | 指標                                     |
| -------- | ---------------------------------------- |
| 正確性   | 建議是否可由保存的官方資料與規則重現     |
| 完整性   | 重要提醒遺漏率、資料限制揭露率           |
| 個人化   | 使用者對行後符合度與建議有用性的問卷評分 |
| 可理解性 | 使用者能否說出建議的站點、時段與原因     |
| 系統性   | API 成功率、資料過期處理率、回應時間     |
